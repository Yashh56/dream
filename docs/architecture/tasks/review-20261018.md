## PRR-01: Pull-request reads are project resources

Status: implemented

Problem: context uses project resources, while detail and pages use a separate
path-only cache, revision counters and a window-wide refresh event.

Agreed scope: consolidate all renderer PR reads in project resources, including
merge information. Key by host and project, repository, PR, action and page.
Successful writes expire only that project's PR resources. Keep drafts,
selection and loaded pages during refresh. Keep writes outside the read cache,
and retain the host's GitHub lookup rules.

Completion criteria:

- No separate PR read cache, window refresh event or view revision counters.
- Detail, loaded pages, context and merge information share resource freshness.
- Explicit host identity follows every panel read/write; stale responses cannot
  cross PR identities. Hidden subscribers refresh when shown again.
- Existing resource and GitHub checks pass; type, lint and scratch checks pass.

Validation (2026-10-18): `pnpm lint`, `pnpm typecheck`,
`pnpm check:scratch` and `git diff --check` pass. Existing resource-cache,
project-resource and host pull-request suites pass (3 files, 25 tests).
Source review confirms host scope on all callers, subscriptions for each loaded
page, scoped expiry replacing in-flight reads, and separate write handling.
No new tests were written. Live GitHub writes, multi-host UI behavior and draft
retention were not exercised in the running app.

Implementation: `pullRequestRead` joins the existing git resource group.
`expireScope` expires the two PR resource kinds only, including hidden readers.
The page hook subscribes to individual pages and preserves the loaded count.
Successful edits update cached detail before refresh. No standalone PR cache,
window event or view revision counter remains.

## HCL-01: Host catalog readiness has one owner

Status: implemented

Problem: connect, connected events and socket resets coordinate reads through
separate paths; a failed reload can be reported as ready.

Agreed scope: a per-host renderer lifecycle owns first-load/reload choice,
pending reads, readiness and supersession. Keep workspace merge/removal rules,
offline snapshots, unsent local changes and catalog write ordering. Invalidate
pending work on disconnect/removal; propagate reload failures. SSH transport
and conflict policy stay with their existing owners.

Completion criteria:

- All three entry paths use the same lifecycle; overlapping loads share work.
- Old reads cannot apply after removal or a newer connection generation.
- Readiness follows successful loading, with failure visible and retryable.
- Existing host/catalog/workspace checks and static checks pass.

Validation (2026-10-18): lint, typecheck, scratch and diff checks pass.
Existing host actions, catalog actions/load/sync, workspace document and catalog
event suites pass (6 files, 52 tests); host actions also passed after the final
resume guard. Existing tests were left unchanged. The real SSH disconnect and
delayed-read scenarios were reviewed in source, not exercised on live hosts.

Implementation: `host-catalog-lifecycle.ts` owns per-store, per-host in-flight
refreshes, first-load/reload choice, connection cancellation and readiness.
Catalog projections and baseline changes run synchronously inside its accepted
read callback. Conflict adoption uses the same read guard. Connect attempts have
identity checks, and removal/disconnect invalidates work before awaiting I/O.
Transport connectivity is retained when only the catalog fails; loaded becomes
false and the error remains visible. Saved baselines survive a disconnect.
