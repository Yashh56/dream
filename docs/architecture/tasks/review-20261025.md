## ARC-01: Agent turn completion

Status: implemented

Problem: observer attachment, final persistence, checkpoint finalization and
queue completion require ordering knowledge in several modules and duplicated
test harnesses.

Scope: one Agent turn execution module owns recording and completion. Keep
provider translation, wire chunks, replay and durable queue policy. Completion
waits for final transcript/session persistence and checkpoint finalization;
checkpoint failure remains best-effort (warn and continue), while persistence
failure fails the run. Stop still reaches the provider; observer disconnection
does not. The scheduler awaits completion without draining a replay subscriber.

Completion criteria:

- Production execution and provider replay tests share completion attachment.
- Delayed/failed final persistence and finalization are tested through execution.
- Stop finalizes after output settles; disconnect leaves execution running.
- Relevant provider, registry, queue, route and checkpoint checks pass.

Validation: 84 tests across 13 execution, queue, registry, provider, route,
checkpoint and session suites passed. Typecheck, lint, scratch and diff checks
passed. Tests use production completion attachment with provider transport
fixtures; no live providers were invoked.

Implementation: `chat/turn-execution.js` owns recorder attachment and final
settlement; `turn-registry.js` offers completion without a replay subscriber.
The three replay/scheduler harnesses now use that production execution module.

Remaining/deferred: none within scope. Live-provider verification is not
established by transport fixtures.

## ARC-02: Connection recovery

Status: accepted

Problem: separate resume subscriptions spread recovery ordering and refusal
policy across sockets, catalogs and chat observers; direct socket connection
attempts bypass the refusal check used by retry timers.

Scope: deepen Connection runtime recovery coordination using existing owners.
Keep transport state separate from catalog readiness, preserve cached drafts,
and introduce no route failover or write replay. Invalidate superseded socket
attempts and catalog reads, and scope chat observation recovery to eligible hosts.

Completion criteria:

- One recovery owner coordinates lifecycle triggers, probes, sockets and reads.
- Refused hosts cannot connect through retain, send, resume or retry timers.
- Late tickets/messages/catalog responses cannot replace current work.
- Recovery tests cover resume, refusal, delayed work and observer reattachment.

Validation: pending.

Remaining/deferred: implementation and validation pending; live phone/SSH
recovery is not claimed by fake-transport tests.

## ARC-03: Remote access state

Status: accepted

Problem: settings polling and mutation refreshes publish the same state with
no shared stale-result rule.

Scope: a Remote access state module owns reads, polling, mutations and accepted
state. Reuse the Route client seam and fake adapter. Keep form drafts, dialogs,
confirmation, QR rendering and translations in the view; authorization stays
on the Host. Do not introduce a generic polling framework.

Completion criteria:

- The view renders module state without coordinating request lifetimes.
- Old polls cannot overwrite a mutation result or a newer list refresh.
- Disposal rejects late results and stops polling; failures preserve good data.
- Tests cover delayed polls, revocation refresh, disposal and read/write errors.
